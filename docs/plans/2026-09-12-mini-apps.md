# Mini apps and phone capabilities

Status: proposed implementation plan, 12 September 2026. Planning only; no
application code, database migrations, billing changes, or deployment included.

## Product decision

Businesses add focused apps inside Jentera. Each app supplies useful screens,
business actions, and optional automations. Connections link those actions to
existing software. Ask Jentera, Activity, permissions, and approvals remain shared.

Start with a first-party **Receipts & Expenses** app: photograph a receipt,
review extracted details, and save an expense draft with its source image.
It works without an accounting connection. Export to an accounting provider is
a subsequent milestone, selected after validating access and the provider's
actual draft-expense contract. This release does not promise bookkeeping,
payments, tax filing, or MyInvois submission.

This extends Solutions in [the architecture](../../TECHNICAL_ARCHITECTURE.md)
and follows [the product thesis](../marketing/product-thesis-and-homepage.md).
A public marketplace remains deferred until useful apps and extension contracts
have been proven.

## Customer experience

1. Open Apps, choose Receipts & Expenses, and see its purpose, access, and usage.
2. The owner adds it to the business and chooses which members may use it.
3. Open the app and choose Take photo or Choose file.
4. Preview the image; retake or cancel locally, or press Use photo to upload.
5. Jentera extracts merchant, date, currency, total, and optional receipt number.
6. Review uncertain or missing fields beside the image and correct them.
7. Save the expense draft. Activity links to the actual draft and source.

Add `/app?view=apps` and `/app?view=apps&app=receipts-expenses`, following
existing navigation. Installed apps appear within Apps; avoid adding a navigation
item for every installation. Support direct links from chat and Activity.
Preserve the mobile navigation pattern, keyboard access, and English/BM copy.
Signed-in empty and loading states must not borrow sample business records.

An owner can access the app's records. Staff explicitly granted app access may
create and view their own drafts; other staff drafts stay private. Sharing an
expense for owner review is explicit in the UI. Workspace-shared records can
follow later. Opening the app from a private chat must not publish that chat or
its attachments; require an explicit import into the expense app.

## App package and lifecycle

V1 apps are reviewed, first-party React modules bundled with Jentera and loaded
through an allowlisted registry. Installation enables an existing module for a
business; it does not download or execute arbitrary code. Native modules in one
JavaScript origin are trusted code: a manifest alone is not a security sandbox.

The versioned manifest is data, validated by frontend and backend. It contains:

- App ID, version, manifest schema version, localized name and description.
- Allowlisted screen, action, and procedure IDs resolved by host registries.
- Required and optional connection capabilities, independent of provider brands.
- Business permissions and device capabilities, each with a user-facing purpose.
- Supported host API version and a platform entitlement key.

For Receipts & Expenses, declare `camera.capture` as optional because file
selection is a fallback, `files.select`, attachment creation, and expense-draft
creation/read/update. No external connection is required. Manifests cannot contain
credentials, arbitrary URLs to execute, or inline executable procedures.

Installation state is `active`, `disabled`, or `uninstalled`, with a pinned app
version and grant revision. Connection health is a separate readiness condition.
Owners manage installations and grants through the central permission table;
app use also requires current membership, entitlement, and app access.

Disabling or uninstalling stops new actions and schedules and invalidates pending
device requests. Jobs recheck grants before each durable mutation or external
action; an already dispatched external action must be reconciled and recorded.
Preserve business records and history, with a read/export path for authorized
users. Uninstallation does not delete records or disconnect a connection another
app uses. Reinstall reuses retained records. Expanded permissions require owner
acceptance before the new version activates; rollback cannot silently undo a
data migration.

## Device bridge

The Jentera host owns the capture UI and device adapters. Apps request a named
capability; the host checks the installed version and user grants, presents the
UI, and returns a narrowly scoped result. The backend repeats authorization for
uploads and all business mutations. A JavaScript check alone is not enforcement.

```ts
// Proposed API: context is bound by the host, never supplied by app code.
const result = await host.device.captureDocument({
  purpose: 'expense-receipt',
  allowFileSelection: true,
});
// { status: 'uploaded', attachmentId } | { status: 'cancelled' }
// Typed failures: unavailable, denied, upload_failed, unsupported_file.
```

Capture and upload are separate internal stages: preview stays local until the
user presses Use photo. The app receives the attachment ID only after durable
upload succeeds. Authorization on each read is still required; the ID is not a
bearer credential. Do not pass camera streams or storage credentials to apps.

Browser permission belongs to Jentera's origin, not an individual mini app.
Jentera's app grants are an additional logical layer. Do not promise a browser
permission prompt on every capture: existing grants may persist and a system
file/camera picker has different permission behaviour from a live camera stream.

Use a file input with `accept="image/*"` and `capture="environment"` for Take
photo, plus a separate input without `capture` for Choose file. The rear-camera
request is a hint whose behaviour varies by browser; desktop may show a file
picker. Real-device verification is required. [MDN capture reference](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Attributes/capture).

If a custom live preview becomes necessary, add `getUserMedia` behind the same
host API. It needs a secure context and user permission. Stop every stream track
on cancel, completion, navigation, or backgrounding; retain file selection as a
fallback. Start capture from a visible host button to preserve user activation.
[MDN getUserMedia reference](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia).

The AI runtime on a cloud computer cannot open the owner's phone camera. Chat
can offer an Open scanner action on the user's device. Scheduled jobs needing
new media become Needs you; they cannot silently collect it.

V1 implements camera capture and file selection only. Later device methods may
cover QR scanning, microphone recording, location, and sharing after individual
compatibility checks. Push continues through the existing notification system.
An installed PWA does not guarantee contacts, NFC, Bluetooth, or background
hardware access. A future native shell can implement the same bridge using native
plugins; it still requires platform-specific permissions and lifecycle work.
Native packaging is not a promise of unrestricted background camera operation.
[Capacitor Camera documentation](https://capacitorjs.com/docs/apis/camera).

## Storage, extraction, and records

Add separate tenant-scoped tables for installations, member app grants,
attachments, and expense drafts. Use typed expense fields and a versioned
extraction payload, rather than a generic app key/value database.

An attachment records business, installation, uploader, purpose, size, verified
media type, hash, private R2 key, lifecycle state, and timestamps. An expense draft
references its attachment, creator, revision, original extraction, reviewed values,
and optional run ID. Composite tenant keys prevent cross-business references.
Keep monetary values as exact decimal values with an explicit currency.

All routes obtain business identity through `resolveTenant` and use `withTenant`
and forced RLS. Add owner-only `apps.manage` centrally. Reads also enforce app
record visibility; tenant isolation alone does not implement staff privacy.
Never use the runtime-authenticated artifact upload endpoint for phone uploads.

Proposed API surface:

| Route | Responsibility |
| --- | --- |
| `GET /api/apps` | Catalog, installed state, grants, and entitlement |
| `PUT /api/apps/:appId/installation` | Owner-managed install/state/version/grants |
| `POST /api/apps/:appId/attachments` | Authenticated bounded image upload |
| `GET /api/apps/:appId/attachments/:id` | Authorized source retrieval |
| `POST /api/apps/receipts-expenses/drafts` | Create draft and queue extraction |
| `GET /api/apps/receipts-expenses/drafts[/:id]` | List or read visible drafts |
| `PATCH /api/apps/receipts-expenses/drafts/:id` | Save reviewed fields with revision check |

For V1, upload through the authenticated Worker to the existing private ARTIFACTS
bucket under a separate attachment prefix. This keeps size enforcement and access
checks in one path. Reconsider signed direct uploads only if measured load merits
them; they would require reservations, expiration, and server finalization.

Proposed input limit: one image per draft, maximum 8 MiB and 20 megapixels after
validation; JPEG, PNG, and WebP. Validate actual bytes and dimensions server-side,
not just extension or declared MIME type. Handle rotation and strip location
metadata from the stored normalized image. Verify a supported bounded image
normalization path in the first spike; unsupported HEIC inputs must produce a
clear conversion/reselection option. PDF, multipage scanning, automatic cropping,
and persistent offline drafts are subsequent features.

Use an idempotency key scoped to business, installation, actor, and operation;
reject reuse with a different payload. An upload reservation precedes the R2 write,
then finalization marks it ready. A reconciliation job handles partial failures;
only finalized, authorized attachments can enter extraction. Automatically expire
unused staging uploads after 24 hours under an explicit temporary-upload policy.
Do not apply that policy to saved source documents or existing artifact prefixes.

Queue extraction durably with bounded retries and metering. Evaluate the existing
document-extraction service against real receipt examples before selecting it.
Store extraction separately from owner edits; never overwrite corrections on a
retry. Unknown values remain empty, and model confidence is only a review hint.
Image text is untrusted input and cannot authorize tools or external actions.

Expense lifecycle: `extracting → needs_review → saved`; extraction failure permits
retry or manual entry. “Saved expense draft” means the local record was persisted.
It never implies posting to accounting software. Subsequent provider export adds
its own proposed/approved/submitted/reconciled states and provider ID.

Keep transient image previews in memory, revoke object URLs, and exclude media
and API responses from service-worker caches. If offline or upload fails, retain
the preview while the page is open and offer Retry; do not claim it is saved.
Refreshing may lose this unsaved preview, which the UI should explain.

Activity records one useful task per receipt and updates it through extraction
and review. Enforce expense visibility in list, detail, notification, attachment,
and agent-tool paths. Do not attach private receipt data to a business-visible
run simply because it originated outside chat. Installation audit events are
administrative records, not counts of completed business work.

## Billing and extension path

V1 uses the platform entitlement system and meters extraction/storage separately
by app ID and installation. Check budget before queueing paid work. Display the
app's inclusion and applicable usage rules; this plan sets no new price and does
not introduce per-app checkout or partner revenue sharing.

Validate reuse with a second first-party app, such as delivery photo evidence,
before freezing an SDK. Camera permission must not grant either app access to the
other's attachments.

Third-party code requires a separate design and release gate: isolated origins,
sandbox/CSP/Permissions Policy, an authenticated bridge bound to the source frame,
exact origin, session, method, and request ID, short-lived scoped server grants,
version review, and revocation. Capture remains in a host-owned sheet with a user
button. Do not load partner scripts into the trusted React host. Any planned data
delivery to a partner backend needs explicit destination disclosure and grants.
[MDN Permissions Policy](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Permissions_Policy)
and [iframe sandbox reference](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe).

## Implementation sequence and acceptance gates

1. **Device and extraction spike.** Verify photo/file capture on physical iPhone
   Safari, iPhone installed PWA, Android Chrome, Android installed PWA, and desktop.
   Check rotation, HEIC handling, denied permission, cancellation, and large photos.
   Evaluate extraction on a consented receipt set with multiple currencies and
   poor lighting. Record field accuracy and cost; choose the normalization and
   extraction path before implementing the full flow.
2. **App foundation.** Add validated registry, installation/grant migrations,
   centralized permissions, repository methods, and Apps UI behind an operator
   feature flag. Verify unauthorized install, staff revocation, version/grant
   changes, disable/reinstall, and real versus anonymous-demo states.
3. **Capture and upload.** Add host device API, preview sheet, attachment storage,
   scoped reads, and reconciliation. Verify actual byte limits, duplicate retries,
   expired membership, foreign attachment IDs, interrupted writes, cancellation,
   and no private media in caches. Use real RLS connections in backend tests.
4. **Receipt outcome.** Add durable extraction, editable draft screen, revision
   checks, app-scoped agent actions, and visible Activity outcomes. Verify retry
   preserves corrections, two saves cannot overwrite newer edits, staff cannot
   read others' drafts, and an app disabled mid-job cannot mutate records.
5. **Pilot release.** Run app typecheck/tests/build and worker typecheck/tests;
   manually visit `/`, `/onboard`, `/setup`, and `/app`, inspect console errors,
   navigation, and mobile layouts. Add before/after screenshots. Release only in
   an intentional deployment, initially to selected businesses. Disabling the
   flag stops new app operations while preserving authorized history access.
6. **Extend after evidence.** Add one validated accounting adapter and a second
   first-party app. Then assess SDK, partner distribution, native shell, and
   billing needs from actual usage.

The pilot succeeds when a business can add the app, photograph a receipt, correct
its details, save it, and retrieve it later with the right access controls.
Track capture-to-saved completion, extraction field corrections, failed uploads,
duplicate records, and cost per saved draft. Set numeric launch targets from the
spike results rather than inventing performance or accuracy claims.

The next implementation unit is step 1: a small capture/normalization/extraction
spike whose output settles the mobile and media assumptions for this plan.
